## Why SystemVerilog for verification
- HDL (Verilog/VHDL) describes synthesizable hardware; HVL features in SystemVerilog
  add OOP, constrained-random, coverage, assertions, and IPC for complex TB construction.
- Pure Verilog TB worked for small designs; modern IPs need CRV, functional coverage,
  self-checking scoreboards, and reusable layered components.
- Older HVLs (Vera, e) still exist historically; verifying Verilog RTL in SystemVerilog
  is the industry default because one language family covers both DUT and TB.

## What a testbench must do (any methodology)
1. Instantiate the DUT with an exact named port map (never invent ports).
2. Generate clocks and apply a legal reset sequence.
3. Drive inputs with directed and/or randomized legal stimulus.
4. Observe outputs and compare to an independent golden / scoreboard.
5. Dump waves (`$dumpfile`/`$dumpvars` or simulator equivalent) and finish cleanly.
Failure modes to avoid: driving DUT outputs, circular goldens (exp = dut_out + 1),
missing clock generators, X on checked outputs after reset without diagnosis.

## Pure SV TB (ChipSutra default / Verilator-friendly)
- Default = LAYERED class TB (NO UVM): interface → generator → driver → monitor →
  scoreboard → env → test → top (`always #5 clk=~clk`, virtual IF, mailboxes).
- Procedural smoke (optional): single `module *_tb` + `$urandom` loop when user asks.
- Driven nets: `logic` with exact widths; never invent ports; independent golden.
- Keep self-checking and seed logging (`void'($urandom(SEED))`).
- Must-know SV pillars: see `sv_fundamentals_must_know.txt` (types, arrays, OOP,
  randomize, constraints, covergroups, SVA, interfaces, IPC).
Maps to ChipSutra methodology=`sv`.

## Methodology ladder (pick what the user asks)
History (short): Vera/e → Synopsys VMM → Accellera OVM (2008) → UVM (2011, IEEE 1800.2).
ChipSutra UI: `sv` | `uvm` | `ovm` | `vmm`.
- `sv`: fastest local path; skeleton + lint; OSS simulators (Verilator/Icarus-friendly subset).
- `uvm`: industry standard class library; agents/sequences/config_db/factory/RAL.
- `ovm`: legacy precursor to UVM; use only when user requires OVM APIs (`ovm_*`).
- `vmm`: legacy Synopsys-style channels/xactors; use only when user requires VMM.
Never mix `uvm_*` and `ovm_*` macros in one TB. Prefer migrating OVM→UVM when possible.

## UVM essentials (when methodology=uvm)
- Hierarchy: test → env → agent(s) → sequencer/driver/monitor + scoreboard/coverage.
- Transaction = `uvm_sequence_item` with `rand` fields matching DUT-relevant inputs.
- Phases: build → connect → run (time-consuming) → extract/check/report.
- Connect pin world via virtual interface + `uvm_config_db#(virtual if)::set/get`.
- Stimulus: sequence `start_item`/`finish_item`; driver `get_next_item`/`item_done`.
- Monitor publishes via analysis port; scoreboard compares predicted vs observed.
- Messaging: `` `uvm_info/`uvm_error/`uvm_fatal `` — not bare `$display` only.
- Factory + config_db enable reuse; RAL when CSR map is provided (do not invent regs).
Forbidden fake APIs: `.put()` as UVM, `.configure(vif)`, `driver.start(this)`, invented phases.
Note: full UVM often needs commercial simulators; ChipSutra does not Verilator-gate UVM.

## OVM essentials (when methodology=ovm)
- Same layered idea as UVM with `ovm_*` base classes/macros and `run_test()`.
- Components: sequence_item, sequencer, driver, monitor, agent, env, test, top.
- Prefer compact legacy skeleton; comment `// ChipSutra methodology=ovm (legacy)`.
- Do not emit UVM-only features (RAL packages, uvm_reg) unless user insists and maps them.
- OVM+VMM in one env: interconnected adapters only (`ovm_vmm_interop_emit.txt`); do not invent wrappers.

## VMM essentials (when methodology=vmm)
- Transaction as `vmm_data` (or equivalent); channels between atomic generators and xactors.
- Driver/monitor as xactors; env wires channels + scoreboard; top starts env.
- Comment `// ChipSutra methodology=vmm (legacy)`; VCS-oriented assumptions OK.
- Keep compact; legal randomized stimulus; exact DUT ports.
- Channel↔TLM / notify↔analysis mapping when mixing with OVM: `ovm_vmm_interop_emit.txt`.

## Learning path (external curriculum map)
Recommended study order for humans (and for expanding this RAG over time):
1. Digital fundamentals → 2. Verilog RTL → 3. Verification concepts →
4. SystemVerilog (types, OOP, random, constraints, coverage, SVA, interfaces, IPC) →
5. UVM (components, phases, sequences, config_db, coverage, RAL).
Accellera UVM User’s Guide 1.2 is the apply-the-library map (`uvm_users_guide_emit.txt`); UG 1.1 is older.
VIP Recommended Practices 1.0 + OVM-VMM interop kit: mix only when asked (`ovm_vmm_interop_emit.txt`).
Primary open tutorial map: https://chipverify.com/tutorials/systemverilog
UVM path: https://chipverify.com/tutorials/uvm
When adding new RAG chunks, prefer short imperative rules + anti-patterns, not essay copies.

## SV language pillars used by every solid TB
- Types: `logic`/`bit`, enums, structs, queues `$`, dynamic/associative arrays.
- OOP: class, extends, virtual methods, handles vs objects, shallow vs deep copy.
- Random: see `sv_constraints_patterns.txt` — `rand`/`randc`, constraints, soft, dist, foreach.
- Interfaces: see `sv_interfaces_patterns.txt` — modports, clocking, virtual IF + config_db.
- Coverage: see `covergroup_patterns.txt` — bins/cross/closure loop.
- Assertions: see `sva_patterns.txt` — concurrent props, bind, formal-friendly bounds.
- Threads/IPC: fork/join*, events, semaphores, mailboxes (layered SV / VIP glue).
